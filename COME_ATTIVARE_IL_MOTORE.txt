COME FAR GIRARE AUTONOMOUS TRADERS CON UN MODELLO VERO
=======================================================

Stato attuale: la demo online mostra dati SIMULATI (generati da backend/demo_seed.py,
nessun modello). Questa guida spiega come passare ad agenti veri che decidono le
operazioni. Comandi pensati per PowerShell, dalla cartella del progetto.


0. COSA SERVE IN GENERALE
-------------------------
- uv, Node 20+ (npx) e git installati (gia' li hai).
- Una chiave per un modello (vedi punto 1).
- TAVILY_API_KEY per la ricerca web (piano gratuito, circa 1000 crediti al mese).
- Facoltativo: NTFY_TOPIC per le notifiche sul telefono (una per ogni operazione).


1. SCEGLI IL MODELLO
--------------------
A) OpenAI (consigliato per affidabilita', A PAGAMENTO)
   .env:  OPENAI_API_KEY=sk-...
          TRADER_MODEL=gpt-5.4-mini
   Costo a consumo. Con 2 cicli al giorno e 3 trader dovrebbe essere basso, ma va
   MISURATO: fai un ciclo di prova e guarda l'utilizzo su platform.openai.com.
   Nota: l'abbonamento Claude Pro NON include l'API, e nemmeno quello ChatGPT.

B) Gemini gratuito (Google AI Studio, INSTABILE)
   .env:  GOOGLE_API_KEY=...
          TRADER_MODEL=gemini-3.5-flash-lite
   Limiti visti sul tuo account (controlla sempre aistudio.google.com/rate-limit):
     Flash Lite: 15 richieste/minuto, 500 richieste/giorno.
     Gemini 3.6 Flash e 3.5 Flash: solo 20 richieste/giorno -> INUTILIZZABILI.
   Problema osservato: errori 503 "high demand" molto frequenti. Il codice riprova
   fino a 6 volte con attese crescenti, ma se Google e' sovraccarico non basta.
   Alternativa da provare: TRADER_MODEL=gemini-3.1-flash-lite.
   Il contatore giornaliero si azzera a mezzanotte ora del Pacifico (circa 9:00
   in Italia), da verificare.

C) Groq gratuito: NON consigliato. Il piano free ha 8.000 token/minuto, troppo
   pochi per un agente con strumenti e ricerche. Il supporto c'e' nel codice
   (TRADER_MODEL=groq:openai/gpt-oss-120b, GROQ_API_KEY) ma nei test ha dato 429.

D) Claude via API: non ancora implementato nel codice (andrebbe aggiunto un client
   in get_model() di backend/traders.py, come per Groq).


2. PROVA IN LOCALE (SEMPRE PRIMA DI PUBBLICARE)
-----------------------------------------------
1) Metti nel file .env le variabili del punto 1 e queste:
     TAVILY_API_KEY=...
     RUN_EVEN_WHEN_MARKET_IS_CLOSED=True      (per provare anche fuori orario)
   ATTENZIONE: il .env vince sulle variabili impostate con $env: in PowerShell
   (il codice usa load_dotenv con override), quindi cambia i valori nel .env.

2) Azzera i conti locali (crea Alpha, Beta, Gamma da 10.000 $):
     uv run -m backend.reset

3) Lancia UN ciclo e misura il tempo:
     $env:RUN_ONCE="true"
     Measure-Command { uv run -m backend.trading_floor | Out-Default }

   I trader girano UNO ALLA VOLTA con 30 secondi di pausa (variabile
   PAUSE_BETWEEN_TRADERS_SECONDS, 0 se il modello e' a pagamento senza limiti
   stretti). Il programma stampa solo alla fine o in caso di errore: per vedere i
   progressi guarda i log nella dashboard o nel database.

4) Esito:
   - Nessuna riga "Error running trader ..." = ok. Devono comparire operazioni
     e (se configurato) le notifiche ntfy.
   - Errore 503: modello sovraccarico. Riprova piu' tardi o cambia modello.
   - Errore 429: limite di richieste/token raggiunto. Aumenta
     PAUSE_BETWEEN_TRADERS_SECONDS o cambia modello.
   - Non lanciare due cicli insieme sullo stesso database.

5) Per guardare la dashboard mentre lavora (tre terminali):
     uv run uvicorn backend.api:app --port 8000
     cd frontend; npm run dev          (poi apri http://localhost:5173)
     (il motore e' il comando del punto 3)


3. PASSARE DAI DATI SIMULATI AI DATI VERI NELLA DEMO ONLINE
-----------------------------------------------------------
Il database pubblicato (data/accounts.db) contiene lo storico INVENTATO della
demo. Prima del primo ciclo vero va azzerato, altrimenti gli agenti proseguono
sopra dati falsi:

     $env:ACCOUNTS_DB="data/accounts.db"
     uv run -m backend.reset
     git add data/accounts.db
     git commit -m "Azzera i dati della demo"
     git push

Poi fai girare un ciclo con lo stesso database (dal workflow, punto 4, oppure in
locale con $env:ACCOUNTS_DB="data/accounts.db" e il comando del punto 2.3) e
committa data/accounts.db: Render aggiorna la demo da solo.

Nel file render.yaml togli il blocco:
     - key: MODEL_LABEL
       value: Simulato
cosi' la dashboard mostra il modello vero invece di "Simulato". Poi commit e push.


4. AGGIORNAMENTO AUTOMATICO CON GITHUB ACTIONS (2 CICLI AL GIORNO)
------------------------------------------------------------------
Il workflow e' .github/workflows/trading-cycle.yml. Ora il cron e' DISATTIVATO.

1) Sul repo GitHub: Settings -> Secrets and variables -> Actions
   Scheda Secrets, aggiungi (solo quelli che usi):
     OPENAI_API_KEY   oppure   GOOGLE_API_KEY   (o GROQ_API_KEY)
     TAVILY_API_KEY
     NTFY_TOPIC       (facoltativo)
   Scheda Variables:
     TRADER_MODEL     es. gpt-5.4-mini   oppure   gemini-3.5-flash-lite

2) Settings -> Actions -> General -> Workflow permissions
   -> "Read and write permissions" -> Save. Senza, il job non puo' committare.

3) Riattiva il cron: nel file del workflow togli i "#" davanti a
     schedule:
       - cron: "0 15,20 * * 1-5"
   (lun-ven, 15:00 e 20:00 UTC, cioe' 2 volte al giorno con la borsa USA aperta).
   Poi git add, commit, push.

4) Prova subito, senza aspettare il cron: scheda Actions -> "Trading cycle" ->
   "Run workflow". Controlla che compaia un commit "Trading cycle ..." su
   data/accounts.db. Se c'e', Render fa il redeploy da solo.

Il job ha un limite di 45 minuti. Su un repo pubblico i minuti sono gratuiti.
Se il workflow fallisce ogni volta (es. Gemini in 503) disattiva di nuovo il cron
per non ricevere email di errore.


5. ATTENZIONE AI PREZZI (MASSIVE)
---------------------------------
Il tuo .env locale ha MASSIVE_API_KEY (prezzi azionari reali). L'API su Render NON
la usa: calcola il valore del portafoglio con il simulatore di prezzi.
Se il motore opera con prezzi reali e l'API valuta con prezzi simulati, i valori
mostrati in dashboard non tornano.
Per avere dati coerenti scegli UNA strada:
  - Non mettere MASSIVE_API_KEY nei secrets di GitHub: motore e API usano il
    simulatore (gli agenti cercano notizie vere ma operano a prezzi simulati).
  - Oppure metti MASSIVE_API_KEY sia nei secrets di GitHub sia in Environment
    del servizio trading-floor-api su Render (attenzione ai limiti di quel piano).


6. PROBLEMI FREQUENTI
---------------------
- "Connection closed" / "Timed out ... 120 seconds": un server MCP o il modello
  non hanno risposto. Riprova; controlla che npx e uv funzionino.
- 503 high demand (Gemini): sovraccarico dei server di Google, non un tuo errore.
- 429 / RateLimitError: quota superata (richieste o token al minuto/giorno).
- Nessuna notifica: controlla NTFY_TOPIC e di essere iscritto allo stesso topic
  nell'app ntfy. Test: uv run -m backend.notifications
- La demo online e' vuota o vecchia: ricarica con Ctrl+F5; l'API gratuita su
  Render si addormenta dopo 15 minuti e la prima richiesta impiega circa un minuto.
- Il .env non va MAI committato (e' nel .gitignore). Controlla con git status
  prima di ogni commit.


7. COSE NON ANCORA VERIFICATE
-----------------------------
- Un ciclo completo di trading con un modello reale in questa versione del codice.
- Il workflow di GitHub Actions eseguito davvero su GitHub.
- Il costo reale per ciclo con un modello a pagamento (va misurato).

Non e' un consiglio finanziario e non esegue ordini veri.
